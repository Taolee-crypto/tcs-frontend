## 1. 프로젝트 정의와 목표

TCS는 특정 음원 유통사에 종속되지 않는 **개방형 글로벌 음악저작권 관리 인프라**다. 창작물과 권리정보를 식별·관리하고, 음악 이용기록을 수집·검증하며, 이용 유형과 적용 정책에 따라 사용료를 산정하고 징수·분배·지급하는 공통 기반을 제공한다. 글로벌 권리관리와 저작권 수입 기반 금융 연계도 지원한다.

TCS의 목적은 기존 저작권 관리체계와 독립적인 유통 플랫폼 사이에 공통 데이터·업무·정산 연결망을 구축하는 데 있다. 협회와 창작자의 기존 권리 및 수익 구조를 존중하면서 플랫폼 간 투명성과 상호운용성을 높인다.

### 1.1 TCS가 수행하는 기능

- 저작물·권리자·권리관계 식별 및 관리
- 신탁계약 및 회원 관련 정보 연계·관리
- 음악 이용정보 수집, 검증, 분류 및 이력 관리
- TL 기준에 따른 이용량 환산과 적용지수 관리
- 저작권 사용료 산정 지원, 징수·분배·지급 업무 지원
- 창작자별 사용내역, 정산내역, 지급내역의 조회
- 독립 플랫폼과의 표준 API 연동
- 글로벌 플랫폼의 이용기록을 공통 TL 단위로 환산하고 창작자별 정산 데이터 관리
- 최종 지급 단계에서 창작자별 납세 관할·소득 유형에 따른 세금 공제 및 국제 지급 정보 관리
- 창작자의 저작권 수입 증명 및 금융기관 연계

### 1.2 TCS가 수행하지 않는 기능

- TCS 자체의 음원 유통·판매 사업
- 특정 유통 플랫폼의 고객·영업·마케팅 사업
- 창작자의 저작권 소유권을 임의로 변경하는 행위
- 협회 정관·규정 또는 법적 근거 없이 회원 자격·의결권을 결정하는 행위
- 금융기관을 대신한 대출 심사·승인·금리 결정
- 근거가 확인되지 않은 저작권료·수수료·정산액의 확정

## 2. TCS와 독립 플랫폼의 관계

### 2.1 상위 인프라와 독립 플랫폼

- **TCS**는 공통 저작권 관리·데이터·정산 인프라다.
- **TIMELINK**는 TCS에 연결되는 첫 번째 독립 음원 플랫폼이다.
- 그 밖의 음원 유통사와 음악 이용 플랫폼도 독립된 사업자·서비스로 운영되며 동일한 공통 기준으로 TCS에 연결될 수 있다.
- TIMELINK는 TCS 내부의 하위 메뉴나 TCS가 소유·운영하는 유통 서비스로 표현하지 않는다.

### 2.2 공정한 플랫폼 연동

1. 모든 참여 플랫폼은 동일한 기본 연동 원칙과 객관적인 이용계약 기준을 적용받는다.
2. 플랫폼별 고객정보, 영업정보, 마케팅정보, 이용정보 및 정산 데이터는 권한과 목적에 따라 분리한다.
3. 특정 플랫폼에 다른 플랫폼보다 우월한 데이터 접근권이나 업무 권한을 부여하지 않는다.
4. TCS는 필요한 권리·이용·정산 데이터만 계약과 동의 범위에서 처리한다.
5. 플랫폼은 계약에 따라 TCS 시스템 이용료 또는 API 연동 수수료를 부담할 수 있다.
6. TCS 이용료와 협회의 기존 저작권 관리수수료는 서로 다른 항목이다. 창작자에게 기존 관리수수료 외의 부당한 중복 비용을 전가하지 않는다.

### 2.3 개념 구조

```text
                     창작자 / 권리자
                            |
                            v
                TCS 공통 저작권 관리 인프라
       권리정보 · 이용기록 · TL 기준 · 정산 · 글로벌 연계
             /              |               \
            /               |                \
           v                v                 v
      TIMELINK         독립 유통사 A       독립 플랫폼 B
      독립 운영           독립 운영           독립 운영
           |                |                 |
           +----------------+-----------------+
                 표준 API / 권리·이용 데이터
                            |
                            v
                협회 관리체계 및 정산 업무
                            |
                            v
                   창작자 저작권 수입
                            |
                            v
                     제휴 금융기관
```

금융기관은 TCS의 공통 데이터 연계 기능을 활용하되, 대출 심사·실행·상환 조건에 관한 책임과 결정권을 독립적으로 가진다.

## 3. 핵심 정책 및 데이터 원칙

### 3.1 TL 적용 기준

기본 단위는 **1초 = 1 TL**이다.

- 기본 TL = 음악 이용시간(초) × 1 TL
- 적용 TL = 기본 TL × 협회가 설정한 적용지수
- 적용지수는 협회가 정책과 규정에 따라 설정·조정한다.
- TCS가 임의로 개별 곡의 경제적 가치나 법정 사용료를 결정하지 않는다.
- 방송·공연·매장·온라인 등 이용 매체와 이용 유형에 따른 적용 기준은 협회가 승인한 정책으로 관리한다.

TL은 이용량을 표준화하고 정책을 적용하기 위한 기준 단위다. TL 수치와 법적으로 확정된 원화 저작권 사용료는 구분한다. TL이 원화 사용료를 자동으로 대체한다고 간주하지 않는다.

### 3.2 적용지수 변경 이력

모든 적용지수에는 다음 정보를 보존한다.

- 지수 값과 적용 대상(매체·이용 유형 등)
- 변경 사유와 정책 근거
- 등록자 및 승인자
- 등록일·승인일·적용 시작일·종료일
- 변경 전후 값 및 변경 이력

정책 변경은 원칙적으로 과거 이용분에 소급 적용하지 않는다. 예외가 필요한 경우에는 명확한 규정·승인 근거와 별도 이력을 남긴다.

### 3.3 회원 자격과 신탁계약의 분리

회원 등급과 신탁계약 상태는 서로 다른 데이터로 관리한다.

- 회원 유형·등급: 준회원, 정회원, 비회원 등
- 권리·계약 관계: 신탁계약 체결 여부, 계약 상태, 계약 범위
- 권리자 유형: 개인 창작자, 음악출판사, 승계자·양수자 등
- 회원 자격, 정회원 승격, 의결권 및 선거권은 현행 협회 정관과 규정에 근거해 판단한다.

신탁계약 체결만으로 정회원 자격이나 의결권이 자동 발생한다고 가정하지 않는다. 확인되지 않은 가입요건이나 수입액 기준을 시스템에 임의로 고정하지 않는다.

### 3.4 정산과 수수료 원칙

- 기존 협회의 저작권 관리수수료율을 초과하는 구조를 만들지 않는다.
- 협회의 기존 수익 기반을 부당하게 감소시키지 않는다.
- 창작자에게 기존 관리수수료와 TCS 인프라 비용을 부당하게 중복 부과하지 않는다.
- TCS 시스템 이용료·API 연동 수수료는 플랫폼 등 계약 당사자와의 별도 계약 구조로 설계한다.
- 예상액, 산정액, 확정액, 지급예정액, 지급완료액을 구분한다.
- 모든 정산 데이터에는 산정 근거, 원천 이용기록, 적용 정책, 처리 시각 및 변경 이력을 연결한다.

### 3.5 저작권 금융 원칙

금융 서비스는 **저작권 수입을 주요 상환 재원으로 삼는 금융 연계**를 기본으로 한다.

1. **저작권료 담보대출**: 지급채권 등 법적으로 담보 설정이 가능한 권리와 과거 저작권 수입 실적을 바탕으로 금융기관이 심사한다.
2. **저작권 수입 기반 신용대출**: 별도 담보가 없더라도 저작권 수입의 실적·지속성·변동성 등을 신용평가에 반영할 수 있다.
3. 금융기관은 대출 심사, 승인, 실행, 금리, 한도 및 상환 조건을 독립적으로 결정한다.
4. TCS와 협회는 창작자의 적법한 동의와 권한 범위 안에서 권리·수입 데이터를 검증·연계한다.
5. 대출 실행만으로 저작권 소유권이나 기존 신탁권리가 자동 이전되는 구조를 만들지 않는다.
6. 담보 설정과 채권 양도 가능성은 개별 권리의 법적 성격 및 계약을 확인한 뒤 처리한다.

## 5. 화면·디자인 시스템 기준

### 5.1 브랜드 방향

TCS는 기존 저작권 관리단체의 상징을 복제하지 않고 독립적인 글로벌 인프라 브랜드를 구축한다. 음악저작권과 창작의 정열·창조성을 연상시키는 주황·빨강·흰색을 중심으로 한다.

초기 디자인 토큰 제안(공식 기관 컬러값이 아닌 TCS 디자인 기준안):

| 역할 | 색상 | 용도 |
|---|---|---|
| Primary Orange | `#F07824` | 주요 액션, 핵심 강조 |
| Primary Red | `#D9272E` | 중요 권리·경고·핵심 지표 |
| Deep Red | `#8F2028` | 보조 강조 |
| White | `#FFFFFF` | 기본 배경 |
| Charcoal | `#333333` | 본문·제목 |
| Light Gray | `#F4F4F4` | 구획·테이블 배경 |

- 주황색을 기본 강조색으로 사용하고 빨강은 핵심 정보에 절제해 사용한다.
- 흰색 기반의 밝고 읽기 쉬운 기업형 UI를 지향한다.
- 본문은 차콜 계열로 가독성을 확보한다.
- Pretendard와 Inter를 기본 글꼴 후보로 사용한다.
- 한국어·영어 전환을 지원하며 문구 길이 변화에 대응한다.
- 반응형 PC·태블릿·모바일 레이아웃을 지원한다.

### 5.2 공통 컴포넌트

- 상단 헤더, 로고, 언어 전환, 로그인·계정 메뉴
- 공개 사이트 내비게이션과 포털 사이드바
- 대시보드 요약 카드 및 통계 영역
- 검색·필터·정렬·페이지네이션
- 표·상세정보 패널·상태 표시
- 입력 폼·파일 제출·확인 단계
- 알림·오류·성공 메시지
- 승인·반려·이의신청 등 업무 액션
- 이력·감사 로그·내보내기
- 접근성 있는 키보드 조작과 명확한 상태 표시

### 5.3 포털별 레이아웃

공통 디자인 시스템을 유지하되 업무 성격에 따라 화면 구조를 달리한다.

- 공개 사이트: 정보 전달 중심의 넓은 콘텐츠 레이아웃
- 창작자 포털: 개인 자산·이용내역·정산·금융을 빠르게 파악하는 대시보드
- 협회 관리자: 검색·검증·승인·정산 등 고밀도 업무형 레이아웃
- 사업자 포털: 계약·API·데이터 제출·연동 상태 중심
- 금융기관 포털: 동의·증명·심사 요청과 접근 이력 중심
- 글로벌: 국가·단체·통화·국제 정산 현황 중심

## 6. 개발 원칙 및 기술 구조

### 6.1 프론트엔드 우선 개발

현재 저장소 `tcs-frontend`는 React + TypeScript + Vite 기반이다. 우선 전체 페이지 구조와 사용자 업무 흐름을 프론트엔드에서 확정한다.

- 기존에 구축된 파일과 동작을 확인하고 보존한다.
- 라우트와 페이지 단위로 순차 구현한다.
- 공통 디자인 시스템을 먼저 정리하고 페이지에 적용한다.
- 화면 이동, 역할별 메뉴 노출, 폼의 입력·검증 흐름을 확인한다.
- 실제 데이터가 연결되지 않은 화면은 확정된 운영 데이터인 것처럼 표현하지 않는다.
- API 연결 전의 예시 데이터는 필요할 때 명확히 데모·예시임을 표시한다.

### 6.2 백엔드 연계 준비

프론트엔드 개발 단계에서도 API와 데이터 계약을 고려한다. 다만 화면을 확정하기 전에 임의의 백엔드 데이터 모델을 사실로 고정하지 않는다.

주요 도메인 후보:
- Identity & Access: 사용자, 역할, 권한, 인증
- Membership: 회원 유형·자격·상태
- Trust Agreement: 신탁계약·범위·상태
- Works & Rights: 저작물·권리자·지분·권리관계
- Usage Records: 이용기록·출처·검증·중복 방지
- TL Policy: 기본 TL·적용지수·정책 버전
- Collection: 산정·청구·수납
- Distribution: 분배·지급·미분배·이의신청
- Platform Integration: 사업자·계약·API·전송 이력
- Finance: 동의·수입 증명·금융기관 요청·심사 상태 연계
- Global: 창작자·납세 관할·플랫폼·TL 정산·세금 공제·국제 지급
- Audit: 접근·변경·승인·정산 감사 로그

### 6.3 보안·개인정보·감사

- 최소 권한 원칙과 역할 기반 접근통제(RBAC)를 적용한다.
- 창작자·협회·플랫폼·금융기관 데이터 영역을 분리한다.
- 개인정보 및 금융 관련 데이터는 목적·동의·보유기간에 따라 접근을 제한한다.
- 중요 조회·다운로드·변경·승인 작업을 감사 로그에 기록한다.
- API 인증정보와 비밀키를 프론트엔드 코드에 포함하지 않는다.
- 권리·정산·금융 데이터의 변경은 변경 전후 값과 처리 주체를 추적할 수 있어야 한다.
- 실제 법률·협회 규정·계약 검토가 필요한 정책은 확인 전까지 확정 규칙으로 구현하지 않는다.

## 7. 단계별 전체 개발 로드맵

### Phase 0. 기준 문서 및 저장소 기반 정리
- 본 마스터 개발계획서를 저장소에 보관한다.
- 프로젝트 구조, 기존 페이지, 라우트, 디자인 및 실행 스크립트를 확인한다.
- 작업 범위와 변경 파일을 관리하고 기존 기능을 보존한다.

**완료 기준:** 기준 문서가 저장소에 반영되고 현재 프론트엔드 구조를 파악한다.

### Phase 1. 공통 디자인 시스템 및 라우팅
- TCS 컬러·타이포그래피·간격·컴포넌트 기준 확정
- 공통 헤더·푸터·내비게이션 구성
- 공개 사이트 및 포털 레이아웃 구분
- 한국어·영어 전환 구조
- 역할별 라우트·메뉴 접근 설계

**완료 기준:** 공통 레이아웃과 전체 메뉴 이동 구조가 연결된다.

### Phase 2. 공개 사이트 전체 페이지
- HOME
- 저작권 관리 안내
- 회원 가입 안내
- 유통사 및 음악 이용사업자
- 저작권 금융
- GLOBAL
- 고객지원

**완료 기준:** 모든 공개 메뉴의 페이지가 존재하고 내부 이동·반응형 화면을 확인한다.

### Phase 3. 창작자 포털
- 대시보드부터 회원·신탁·저작물·TL 자산·이용내역·정산·금융·글로벌·커뮤니티 순으로 구현
- 조회·등록·신청·이의제기 흐름 정의
- 개인별 데이터 접근 경계 반영

**완료 기준:** 창작자의 주요 업무 여정을 화면에서 처음부터 끝까지 따라갈 수 있다.

### Phase 4. 협회 관리자 포털
- 통합 대시보드
- 회원·신탁·저작물·권리 관리
- 이용기록 검증
- TL 적용지수 정책과 승인 이력
- 징수·분배·지급
- 금융·플랫폼·글로벌·시스템 관리

**완료 기준:** 협회 담당자의 검증·승인·정산 업무 흐름과 관리자 권한이 구분된다.

### Phase 5. 유통사·음악 이용사업자 포털
- 사업자 등록·계약
- 저작물 메타데이터 매핑
- 이용기록 제출·검증
- 정산 데이터 교환
- API 문서·인증·테스트·장애 지원
- 이용료·계약 이력

**완료 기준:** 독립 플랫폼이 표준 연동 절차를 이해하고 업무 흐름을 수행할 수 있다.

### Phase 6. 금융기관 제휴 포털
- 제휴기관·담당자 관리
- 창작자 동의 확인
- 저작권 수입 증명 요청·검증
- 대출 심사 요청·상태 회신
- 담보 관련 확인 및 상환 연계
- 접근·처리 이력

**완료 기준:** 금융기관 권한이 협회 권한과 분리되고 동의 기반 정보 연계 흐름이 정의된다.

### Phase 7. 글로벌 TL 정산·세금 공제
- 글로벌 창작자 프로필과 납세 관할 정보
- 독립 플랫폼의 이용기록 수신 및 공통 TL 환산
- 창작자별 TL 배분과 정산 확정
- 국가별 세금 공제 정책·소득 유형·조세조약 검토 구조

- 국제 지급 상태 및 세금·지급 증빙

**완료 기준:** 국가별 저작권협회 연계 없이 공통 TL 정산과 창작자별 세금 공제·지급 흐름을 설계하고, 법률 검토가 필요한 세율 적용 근거를 추적할 수 있다.

### Phase 8. 화면·업무 흐름 통합 검증

**완료 기준:** 정의된 화면과 업무 흐름에서 끊김·중복·권한 혼선이 해결된다.

### Phase 9. 백엔드 API·DB 및 외부 시스템 연동

**완료 기준:** 프론트엔드 화면이 검증된 실제 데이터와 권한 정책에 따라 동작한다.

## 8. 검증·인수 기준

각 페이지는 단순히 화면이 보이는 것만으로 완료 처리하지 않는다. 다음 항목을 확인한다.

1. 페이지가 올바른 URL에서 열리는가?
2. 상위·하위 메뉴와 뒤로가기 흐름이 자연스러운가?
3. 화면 제목·설명·액션이 해당 사용자 역할과 일치하는가?
4. 입력값 검증과 오류 메시지가 있는가?
5. 로딩·빈 데이터·실패 상태가 구분되는가?
6. 권한이 없는 사용자가 데이터나 액션에 접근할 수 없는가?
7. 개인정보·금융정보가 권한 범위를 벗어나 노출되지 않는가?
8. PC·모바일에서 레이아웃이 깨지지 않는가?
9. 한국어·영어 전환 시 레이아웃과 문구가 정상인가?
10. 실제 연동 전의 예시 데이터가 운영 데이터로 오인되지 않는가?

빌드·테스트·배포 여부는 실제 명령 실행과 결과 확인 후에만 완료로 기록한다.

## 9. 변경 관리 및 의사결정 원칙

- 본 문서는 TCS의 공통 사업·제품·개발 기준이다.
- 정책 변경은 문서 버전과 변경 이력을 남긴다.
- 확정된 원칙과 검토 중인 제안은 구분한다.
- 협회 규정·법률·계약 확인이 필요한 항목은 근거 확인 전까지 확정하지 않는다.
- 기존 TIMELINK 프로젝트와 저장소의 파일·기능을 임의로 삭제하거나 변경하지 않는다.
- TCS 프론트엔드 변경은 `tcs-frontend` 저장소 범위에서 수행한다.
- 기존 기능을 수정할 때는 변경 범위와 영향 페이지를 확인하고, 불필요한 전체 교체를 피한다.
- 기능 완료는 코드 반영, 빌드 확인, 화면·업무 흐름 검증을 구분해 기록한다.

## 10. 현재 개발 위치와 바로 다음 작업

현재 저장소에는 React + TypeScript + Vite 기반의 공개 홈페이지 초기 골격과 기본 라우팅·디자인이 반영되어 있다. 다만 실제 로컬 설치·빌드·브라우저 검증 여부는 별도로 확인해야 하며, 확인 전에는 빌드 성공으로 간주하지 않는다.

다음 작업 순서:

1. 저장소의 현재 파일과 라우트 구조를 다시 확인한다.
2. 의존성 설치 및 프로덕션 빌드를 실행해 실제 오류를 확인한다.
3. 공통 디자인 시스템과 전체 라우트 구조를 정리한다.
4. 공개 사이트의 각 메뉴 페이지를 완성한다.
5. 창작자·협회·사업자·금융기관 포털을 순서대로 구현한다.
6. 전체 화면과 업무 흐름을 검증한 뒤 백엔드 API·DB를 구축한다.

**최종 지향점:** TCS는 어느 한 유통 플랫폼의 부속 서비스가 아니라, 다양한 독립 플랫폼과 권리자·협회·금융기관이 공정한 기준으로 연결되는 글로벌 음악저작권 관리 인프라다.
